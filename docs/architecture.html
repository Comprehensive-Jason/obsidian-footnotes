Footnote Shortcut · plugin structure

What the plugin is made of, one layer at a time

Four layers of source code stacked so that each one only leans on the layer below it, wrapped in a testing scaffold that is bigger than the plugin itself. This page walks the stack from the bottom up.

Claude: drafted 2026-09-09 from a read of the code and kept current through 2026-10-03 (version 0.3.0-beta.2, the September 2026 feature round, and the runtime swap that moved the plugin onto Obsidian's own parser; the counts are from the tree on that day). Terms follow CONTEXT.md: a reference is the [^1] in your text, a definition is the [^1]: … line that holds the note.

0The whole thing in four sentences

  1. Parsing reads your note once, the way Obsidian reads it, and tells everyone else what is real: which text is protected (code, math, comments, frontmatter), which [^x] are live references, which [^x]: lines are true definitions, and where each definition ends.
  2. A press of a hotkey falls down a fixed ladder of questions (is there a selection? several carets? is the caret already on a footnote?) and the first rung that applies handles it. Nothing is written until a rehearsal proves the new footnote would actually work.
  3. Lint is eight small text-in, text-out functions run in a fixed order inside one undo step. Anything lint refuses to fix on its own, it tells you about in a notice.
  4. Everything outside src/ exists to prove those three sentences stay true after every change: unit tests, random-document properties, mutation testing, a script that drives the real app, and 20 manual sheets.

If you remember only this list, you can find your way around. The rest of the page fills in each sentence.

The parsing files import nothing from the layers above, with the one exception below. The note reading, the parser it is built on, and the small text walks around them are pure text logic: give them lines, get back facts about those lines. That is why they can be tested thousands of times per second without Obsidian running, and why the mutation tester can chew on them.

A few imports do point the wrong way, and they are worth knowing about because they are where the layers leak. The prefix reader in parsing imports the notice helper and the plugin class. The linter imports the popup and one navigation jump from commands, because lint on save has to close an open popup first and the after-creation lint has to land the caret. (The lint alerts used to import the inline-footnote scanner from commands too; since the runtime swap of 2026-10-03 the inline footnotes come from the note reading.) None of these is a bug, but each one is a reason the "parsing is pure" claim is true of the reading and the grammar, not the whole folder.

2Parsing: reading the note

Everything above this layer asks it the same few questions. Is this spot protected? Is this [^x] a live reference? Is this line a real definition, and where does it end? The answers are harder than they look because Obsidian's Markdown has a lot of places where [^1] is just text.

The note reading: Obsidian's own parser, rebuilt

Every answer comes from the note reading (parsing/note-reading.ts): one parse of the note the way Obsidian reads it. Obsidian's Reading view, its metadata cache, and Publish share one Markdown parser, a fork of remark-parse 8, so parsing/obsidian-markdown.ts starts from the real remark-parse 8 with the footnote and math plugins of the same era and adds Obsidian's own rules on top, each written from Obsidian's observed answers and named by letter and number in docs/obsidian-reading-rules.md: callouts, wikilinks, %% comments, tables, frontmatter, and the rest. parsing/footnote-facts.ts reads what the plugin needs off the tree: every definition with its last line and its container, every reference with whether it is live, every stretch of protected text, the block syntax at the start of each line, the table rows, and the inline footnotes. Until October 2026 a hand-written scanner of about 2,800 lines answered these questions by approximating each rule; the runtime swap of 2026-10-03 replaced it in four steps (definitions, then protected text, then references, then deleting what was left).

The reader is held to Obsidian by the referee: scripts/oracle asks the live app (its metadata cache and Reading view) about notes and saves the answers, and test/obsidian-referee.test.ts checks the reader against about 6,800 of them on every test run, failing on any disagreement but three known spots where Obsidian's metadata cache reports a wrong column.

Parts, remembered by their text

Parsing a long note takes a noticeable moment, more on a phone, and a press reads the note several times (as it is, with the new reference, with the new definition). So the reading parses a note in parts and remembers each part by its exact text: an edit changes one part, and a read after an edit parses only that part again. A part may start at a line in the first column after a blank line, or at a label line, picked by a small hash of the line's own text so that an edit never moves the part starts around it. Each part is parsed together with the first line of the next, and ends cleanly only when that borrowed line starts a block of its own; when it does not (a fence still open, a list going on, a link definition's label still open), the part is tried again with more of the note joined to it. test/note-reading-parts.test.ts holds the reading in parts to one parse of the whole note, over every saved Obsidian answer and thousands of generated notes edited at random. On the sandbox vault's speed-test notes (desktop, 2026-10-03), a press after an edit takes about 10, 42, and 133 ms on notes of 1,091, 5,634, and 22,386 lines, and a full lint about 24, 71, and 292 ms.

Protected text and the masked twin

A code block, an inline code span, a math span, an HTML comment or block, the frontmatter, a link's destination, and a wikilink's inside are all places where footnote syntax means nothing. The reading knows each one as a stretch of protected text, and builds from them the masked twin: a copy of the note where every protected character is replaced by a blank placeholder (a NUL byte) of the same width. The rules are Obsidian's, not a spec's: a closing dollar sign that is directly followed by a digit does not close a math span, so "pay $5 or [^1]$6" is prose with a live reference, exactly as Reading view shows it.

raw line See [^1] and `not [^2]` and $x^[^3]$ here. masked twin See [^1] and `not [^2]` and $x^[^3]$ here. column 0····5····10···15···20···25···30···35···40···45

Figure 2. The twin is the same length as the original, so column 4 on the twin is column 4 on the raw line. Which references are live the reading says itself; the twin answers the few questions it does not, such as where an empty [^] placeholder sits or where the punctuation after a word ends. Only the green [^1] is live; the two red ones are fakes.

Why a same-length copy instead of just deleting the protected parts? Because every position the reading finds has to be handed to the editor as a line and column to edit. Keeping the widths identical means nobody has to translate coordinates, and every column the reading reports is a column in the text: where Obsidian's own metadata cache misplaces one (text after a %% on its line), the reader keeps the true column and the referee lists the difference.

Obsidian's own comments are the odd one out

Obsidian's %% %% comments are hidden in Reading view, but Obsidian still parses them. Checked against the live app: a reference inside a comment binds to its definition and takes a number in order of appearance (only its superscript is hidden), while a definition inside a block comment is dead. So the reading reads a comment's text like any other, and its references count (Jason's ruling A1), while the masked twin leaves the comment's text in place; the lint names a label written inside a block comment. A %% alone at the start of a line opens a block that runs to the next %% anywhere later; a pair on one line is an inline comment.

Definition starts and the lazy label

A line that looks like [^1]: text is usually a definition. But if it sits directly under a line of prose with no blank line between, Obsidian treats it as a continuation of that paragraph, plain text with a live [^1] reference in it. The project calls this a lazy label. The reading says which label lines start a definition, and parsing/label-shapes.ts finds the label-shaped lines it says do not, so the lint can name them, the fix-lazy rule can give them their missing blank line (section 4), and a press or a deletion can treat them as the definitions they were meant to be. A label with a setext underline under it is the same story in the other direction: a heading's text, one blank line short of a definition.

The reading gives every definition its last line, so each is a definition block: the label line plus its continuation lines and the blank lines between them. Blocks are the unit that gets moved to the bottom, merged, or jumped to.

The note reading and definitions in containers

Which lines are definitions, and where each one ends, now comes from the note reading (parsing/note-reading.ts): one parse of the note with parsing/obsidian-markdown.ts, the remark-parse 8 reader the referee suite holds to Obsidian's own answers, remembered per exact text so a press or a lint parses each text once. Every definition counts wherever it sits, at the top level, in a quote or callout, in a list item, or inside another footnote, and each carries its container (Jason's ruling 1, option a, 2026-10-03). Only a movable one, at the top level with nothing but indentation before its label, is ever moved to the bottom or reordered; one in a container stays where it is, and a rule that cannot safely edit it refuses or alerts.

DocContext: one reading per press

A hotkey press builds one DocContext in editor/doc-context.ts. It reads the note once and answers every later question from that one reading: the live references on a line, the reference at the caret, the definitions, the masked version of a line. The whole cascade of decisions in the next section shares that one object, and a check of the note as it will be after the edit is one more reading, mostly of parts already read.

Lint is different by design: each rule takes a string and returns a string, so each rule builds its own view of the note. That is what lets every rule be tested on its own. The reading remembers each text it read and the parts of the last eight readings, so rules that receive the identical text share one reading, and a rule's output reads mostly from parts already read. On the 22,386-line speed-test note a full lint after an edit takes about three tenths of a second, and a normal note lints in a few milliseconds.

The prefix reader

parsing/footnote-prefix.ts reads the footnote-prefix property out of the frontmatter with a hand-written reader rather than a real YAML parser, on purpose, so it can run on every keystroke without asking Obsidian's metadata cache. It also enforces two odd rules that come from Obsidian itself: a prefix may not end in a digit (it would collide with plain numbering on reindex) and may not contain # (it breaks Obsidian's footnote hover preview).

Whole-note commands share one shape

Delete footnote everywhere, both style conversions, the carried paste, and the lint itself all work the same way: a pure function turns the note's text into new text, and one shared write-back in editor/write-back.ts puts the result into the editor as the smallest set of line edits, in one transaction, keeping folds, the caret, and any second pane on the same note where they were. Only the parts that need the live editor (the paste event, the inline-to-normal conversion, which reuses the definition placement) are built editor-side. The pure part can then be property-tested with the same random-document generator the lint rules use. This is the standing rule for any new whole-note feature.

Rehearsing before writing

The "born dead" check is the idea that explains a lot of the code's size. Inserting [^3] at a spot can be swallowed by a backslash before it, or can accidentally close an open $ math span so the whole thing becomes math. So editor/insertion-liveness.ts applies the planned edit to a copy of the note, reads the copy, and checks that the new reference and definition are live footnotes in it. If not, the press is refused. Multi-caret presses do this for every caret and refuse the entire batch if one would die.

Where the reference lands

A reference inserted mid-word is moved to the end of the word first. It then steps past every closing mark after the word: closing quotes straight and curly, brackets, the bold and italic markers, a link's (url) tail as a whole, and trailing punctuation. So a footnote on the last word of "some bravo". lands after the quote and the full stop under the default placement, which is what English, Taiwanese, Korean, and Dutch writing do; the Placement relative to punctuation setting (2026-09-21) can instead stop the walk in front of the punctuation, as mainland Chinese, Japanese, French and the EU style guide do, or leave the reference exactly at the end of the word, stepping over nothing, not even a closing quote (Jason, 2026-09-22: Don't move means what it says). One walk in parsing/landing.ts decides this, and the same walk drives the punctuation lint rule, so a note typed the old way lints into the shape the insert now produces.

Where the definition lands

commands/definition-append.ts decides placement in three steps: right after the last existing definition block if there is one; otherwise under the section heading if that setting is on and the heading exists; otherwise at the end of the note, stepping back over trailing blank lines and over any unclosed code fence or math block so the definition never lands inside dead text.

Selection conversion

The 1,135-line selection-footnote.ts handles one thing: turning highlighted text into a footnote. It is long because the refusals are many. It trims whitespace edges, optionally widens to whole words, then refuses selections that cut through a table, cut through protected text, or touch any existing footnote (the plugin never nests footnotes, by decision, see ADR-0001). For the named command it has to open a dialog to ask for a name, and that dialog steals the plugin's own hotkeys so pressing the key again submits it instead of opening a second one. When the selected text begins with a code fence, the definition gets an empty label line and the fence starts on the next line; every other block (a heading, a table, a list, a quote, a math block) shares the label line, because Obsidian renders those there.

The three text dialogs

Name the footnote, Rename footnote, and Set footnote prefix share one base in validated-text-modal.ts: an explanation, one text box, an error line, and Obsidian's own button row. They are built the way Obsidian builds its Rename heading dialog, so Obsidian's stylesheet places them: a compact centred dialog on the desktop, and on a phone a bottom sheet that Obsidian lifts above the on-screen keyboard. A refused value keeps the field focused and selected, so the correction can be typed at once.

The popup

The at-cursor editor for a definition is not a custom editor. It is Obsidian's own embed renderer, the thing that draws ![[note#heading]], pointed at a subpath of the form #[^id] and switched into editable mode. This trick means the popup is a real Obsidian editor with real behaviour, and it means the plugin depends on an undocumented internal. Because embeds resolve through the metadata cache, the popup can only open once the cache has caught up with your edit, which is what popup-retry.ts waits for: it listens for cache changes, polls slowly as a fallback, shows a "waiting" notice after a second, and gives up after twenty by jumping to the definition instead. Two details worth knowing: a footnote defined more than once skips the popup and jumps to the last definition, the one Obsidian renders, because the embed lookup would find the first; and the label beside the editor copies the embedded editor's font metrics and the core Footnotes view's theme variables, so the two line up on every device and theme. When the popup saves, it writes the definition back through the same shared write-back the lint uses, so the note keeps its folds and caret.

Table cells

When you edit a table cell in Live Preview, Obsidian opens a hidden second editor just for that cell, and the main editor's caret position goes stale. editor/table-cursor.ts finds the real caret through the focused DOM element and maps cell coordinates back to note coordinates. Every write into an active cell goes through the cell's own editor, because writing to the main editor at the same time corrupts the table (issue #28). Obsidian can also leave a cell's caret pointing past the end of the cell's text after it rebuilds the cell, so every cell read clamps the caret to the text first. This is why a creation in a cell can take two undo steps, and why the partial-undo notice says whether a second undo will remove the reference.

4Lint: the cleanup pipeline

A lint rule is a function that takes the note as a string and returns the note as a string. Eight of them exist. The linter runs the enabled ones in a fixed order, hand-written in linting/linter.ts with a reason at each step, and the result is written back through editor/write-back.ts as the smallest set of line edits, worked out by editor/document-diff.ts, inside one editor transaction, so one undo reverts the whole lint. Untouched lines are never rewritten, so a caret in them stays put. Obsidian drops a heading's fold on any edit inside it, so before writing the write-back also reads the view's folded ranges, carries their line numbers through the edits, and puts them back afterwards; a second pane showing the same note is put back by line too, since scroll pixels drift when line heights are re-estimated. A ninth transform runs after the eight rules when its toggle is on: the empty-heading sweep removes the footnote section heading once nothing is left under it. It reaches each rule through that rule's entry in the catalogue in rules/index.ts, and a test watches those calls and fails if the catalogue's order and the linter's ever differ, so the catalogue can be trusted as a description of the pipeline.

Why the order matters

The blank-line fix runs before everything so that every later rule judges the definition you meant, not the prose line Obsidian saw: move-to-bottom gathers it, the orphan and duplicate rules see an ordinary orphan or duplicate, reindex numbers it. Merging next means every later rule sees one block per name. Definitions are deleted before references because deleting a reference can never orphan a definition, but the reverse order could flip verdicts between passes. Orphaned references are judged after the move so the geometry-based refusal guard sees the settled layout. Reindex goes last because it is the only rule that changes names, and it needs the prefix resolved first so it can number prefixed and plain footnotes in their own namespaces.

Reindex has its own inner loop. Reordering definition blocks can change the first-use order of references nested in continuation lines, which calls for another pass. It repeats up to thirty times until nothing changes. Some documents never settle (a three-way cycle exists in the tests), so it detects the repeat and picks a canonical member of the cycle rather than rewriting your file forever on every save.

Three ways lint gets triggered

  • The command. Closes any open popup, then runs the pipeline.
  • On save. The plugin wraps Obsidian's own save command so lint runs just before the write. Vim's :w bypasses that command entirely, so a second hook redefines vim's write command to route through it.
  • After creating a footnote. Runs before the popup opens so you never see un-linted text, and returns the possibly renumbered name so the caret can find the footnote again.

All three refuse to run in Reading view, while a popup or table cell owns focus, or when the note's prefix is invalid (reindexing would then collide prefixed and plain numbers).

Never silent. Every rule that can destroy text is off by default, and when it is off the same condition becomes an alert instead (ADR-0002). So "Footnotes linted" followed by three notices is the design working, not a contradiction. The alerts module asks one reading for all its checks and reports empty placeholders, orphans, lazy labels, labels underlined into a setext heading, duplicates, nesting, invalid names, labels inside %% block comments, and definitions written inside tables.

Two undo safety nets that are unrelated

The first is the single-transaction lint above. The second, editor/undo-orphan-notice.ts, watches the editor's own undo. When an undo removes a definition and strands its reference, the extension says so in a notice, and dismisses itself once the orphan is gone. It only promises that a second undo will remove the reference when the plugin itself split the creation into two history steps, which happens for the numbered key, the paste key, and a selection conversion inside a table cell; for a reference you typed by hand it states the fact and stops.

5Plumbing: main.ts, settings, and the danger zone

main.ts is the only file Obsidian loads. On load it registers the ten commands and nine hand-drawn icons, installs the save hook and the vim hook, registers the undo-orphan extension, wires the right-click rename and delete entries, installs the copy, cut, and paste hooks that carry footnote definitions along, and runs settings migrations. On unload it puts everything back.

settings.ts holds the settings interface, the defaults, and the settings tab, written against the declarative settings API in Obsidian 1.13. The migrations live in main.ts: version 1 renamed every tidy* key to lint* when the feature was renamed, version 2 flipped the polarity of the orphan-definition toggle, and version 3 folded the old renumber-named-footnotes toggle into the three-way naming style. The settings page is laid out loose-first: the popup and carry toggles at the top, then the groups Footnote reference placement, Footnote names, and Footnotes section, then the lint groups. Descriptions are written with a small markup helper, so a setting or command name is bold and syntax is in code font. Loading also type-checks every saved key against the defaults and drops mismatches, so a hand-edited "no" cannot be read as true.

editor/obsidian-internals.ts is the deliberate quarantine for everything undocumented: the raw CodeMirror view behind the editor, the embed registry the popup hijacks, the property type manager, the hotkey manager (so the name modal can read your real key bindings), vim's internal state (so Escape in the popup can tell insert mode from normal mode), and the command executor. Every access is optional-chained so a future Obsidian release degrades a feature rather than crashing the plugin. Anything that touches this file is smoke-test territory, not unit-test territory, because a mocked test would only encode the plugin's own assumptions.

6The scaffold: five ways of checking

This is where most of the file count lives, and why the repo feels much larger than a 17,000-line plugin. Each layer catches a different kind of mistake, and each is coloured here by the part of the plugin it mostly protects.

1Unit and property testsnpm test · 567 files100 feature specs, 23 files that pin what the retired manual sheets used to ask a human, and under test/hunt/ 316 bug pins and 123 spec rulings. The referee holds the reader to Obsidian's saved answers, and the parts test holds the reading in parts to one parse of the whole note. Plus the properties: random documents are generated, linted, and checked for invariants like "no NUL leaks", "protected text is byte-identical", and a differential oracle that parses each document with an independent Markdown parser before and after and demands the same footnote structure. Continuous integration on GitHub runs only layers 1 and 2 plus the build. The rest is a pre-release ritual you run by hand.

Why there are 316 bug files

The standing rule is that every bug found gets a failing test before it is fixed, and the test stays forever as a regression pin. That many pins means that many bugs were found and fixed that way, most of them by the adversarial hunts (in mid-September 2026 alone, five Kimi cycles, ten GLM cycles, and one Opus cycle found and fixed about a hundred) and the property suite. The spec rulings next to them pin behaviour Jason ruled on after a hunt asked whether it was a bug. They are not clutter you need to read; they are a ratchet. Delete one and the bug it pins can come back unnoticed.

Things that look like duplicates but are not

  • One README. The 0.2.0 rewrite replaced the 0.1.3 README.md on 2026-09-11; every GIF and still in README/ is recorded by scripts/readme-gifs/record.mjs.
  • Three manifests. manifest.json is the shipped 0.2.0, manifest-beta.json is the in-flight beta (0.3.0-beta.2 as of 2026-09-25), and versions.json maps each release to the minimum Obsidian version, which Obsidian's installer requires.
  • Two vitest configs. The fast one shares workers; the Stryker one isolates per file because mutation coverage tracking needs it.

7Where the complexity actually comes from

It is fair to ask whether seventeen thousand lines is too many for footnotes. Here is an honest accounting of what the lines are paying for.

  • Obsidian's Markdown has terrain. Code, math, both kinds of comment, frontmatter, blockquotes, lists, tables, lazy labels, setext headings. Each one is a rule of Obsidian's parser, and each rule interacts with the others (a fence inside a blockquote closes when the quote ends). Since the runtime swap the plugin reads notes with that parser, rebuilt (section 2), instead of approximating each rule by hand; the parsing folder is a fifth of the plugin by lines, and every layer above it still carries guards for the same terrain.
  • The plugin promises never to eat your text. That promise is why every insertion is rehearsed first, why lint refuses edits that would reclassify a line, why destructive rules are off and alert instead, and why selection conversion has more refusals than conversions.
  • Two features sit on undocumented ground. Table-cell editing and the popup both work by reaching into Obsidian internals, and each needs a recovery path for when those internals misbehave.
  • The tests outnumber the code by design. Bug pins accumulate, properties are expensive to write well, and the smoke script is a small program of its own.
  • About 40% of the source lines are comments. On 2026-09-09 every comment was rewritten in plain language, with the point first, the reason second, and the history (rulings, dates, issue numbers) kept. That added roughly 1,500 lines and no code. The line counts on this page include them.
